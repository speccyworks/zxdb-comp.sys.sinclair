The .DCK format doesn't need any modification. It allows you to define the
entire 192K memory map of the Timex machines. You can set which pages are
RAM and which are ROM and you can provide data for any pages you want. You
can define the data for only one or two banks (DOCK, EX, HOME) so the
files are no longer than they have to be. Whatever banks you don't define
default to the standard setting for that bank.

When dealing with Timexes it's best to talk about the two different
machines separately. The TC2048 was close enough to the original 48K
Spectrum that it will run most software intended for that machine. It has
an almost exactly identical version of the original ROM but there are a
handful of programs that use the extra video modes of this machine
including Basic 64 (TC2048).

Then you have the TS2068/TC2068/UK2086. These machines have a different
ROM and will not be able to run any Spectrum or Timex 2048 program that
relies on ROM routines appearing at a specific location (without using an
emulator). The result is that, with the exception of a very few games
which use no ROM code, like the early 16K releases and JSW and MM,
virtually no Spectrum games or other software will work on this machine

I haven't checked that yet, but I did try Fairlight again, and I could
hear the problem. There's definitely some aliasing noise, but it's
hard to know what to do about it - it'd need an *extremely* aggressive
low-pass filter to compensate, which would probably just end up making
things sound worse.

What it *seems* to be trying to do is treating the beeper as a 3-level
device, toggling the beeper very fast to fake the `middle' level. This
generates a 36.5kHz tone (!), or it would if the frequency response of
everything involved was up to the task (not that you'd be able to hear
it even if it were).

Fuse effectively takes the average of the beeper output over the
length of each output sample, so in theory it should cope with this
ok... except that it's more complicated than that. The phase of the
36.5kHz tone `slips' relative to the sample rate over time, so you get
rather small amplitude (but still audible) aliasing noise. With Fuse's
usual 32kHz output this seems to be at 4kHz or so. At 44.1kHz it moves
to nearer 8kHz (maybe 7.5kHz? I haven't checked it too closely).

I suppose what's really required to do the job properly is to generate
a beeper-output sample at 3.5MHz, then resample that very carefully
(with appropriate filtering) to the actual sample rate you want to
write. Maybe that isn't as crazy as it sounds these days, but for the
sort of filtering I think would be required it would take truly evil
amounts of CPU time.

I really wonder, am I missing some obviously better approach here?
