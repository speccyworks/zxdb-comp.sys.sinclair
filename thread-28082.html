Just a quick post to announce that version 1.1 of the zxUSB addon is now 
up on the web.

Q. What is zxUSB?

A. zxUSB is an attempt to get a working USB controller on to the humble 
speccy.  It is based on the NatSemi USBN9603 USB controller IC.


Q. What software exists?

A. None at present.  If you are seriously interested in writing a driver 
for a piece of hardware, then contact me and I'll try to make a 
development board available to you.


Q. Where can I find it then?

A. Glad you asked that.  Take a look at:

http://8bitorbust.info/sinclair/spectrum/hardware/zxUSB/RELEASE1.0/


Questions / comments / really silly mistakes to point out ?

cheers,
Dave

have some compelling reason to keep it on NMI.  A free way to get IM2

The /INT line is open collector so you can have as many interrupting
peripherals as you want share the line.

I'm currently writing some documentation on IM2 so I'll just copy a
snippet that explains how IM2 works from the software point of view:

"
IM2 is the most powerful interrupt mode and is activated by executing
the 'IM 2' instruction. This is a vectored interrupt mode: when the
Z80 acknowledges the interrupt, the interrupting peripheral is
expected to supply an 8-bit identifier.  The contents of the 'I'
register and the 8-bit identifier are concatenated (with 'I' being the
most significant 8-bits) to form a 16-bit address that contains the
address of the interrupt service routine to jump to.  Effectively,
I*256 points at a 256 byte table that contains interrupt service
routine addresses.  The peripheral supplies the index into the table
to find the right interrupt service routine.  By
convention, the interrupting peripheral's identifier is even to make
things work smoothly.  This ensures that table entries do not collide.
 Eg: A peripheral with ID 0 uses addresses I*256+0 and I*256+1 to
store its interrupt service routine address.  Peripheral ID 2 uses
addresses I*256+2 and I*256+3 to store its ISR address.  A peripheral
with ID 1 would have table
addresses that conflict with both.

That said, the Spectrum's sole interrupter (the ULA) was not designed
for working in IM2.  It does not supply an identifier when the Z80
expects one.  However, since nothing controls the data bus at the
appropriate time, passive resistors pull the data bus value to a
predictable value: 255.  The Z80 will therefore see a peripheral ID of
255 whenever the ULA interrupts.  This is
an odd value that will cause an ISR fetch from table addresses
I*256+255 and I*256+256.  For the Spectrum, therefore, we'll need a
257 byte interrupt vector table.  Everything is not gold in Spectrum
land, however.  Certain common Spectrum peripherals (Kempston joystick
for one) were improperly designed and could spew random data on the
data bus when the Z80 is looking for a peripheral ID.  Therefore, with
a Kempston joystick attached, the ULA's peripheral id could become a
random bit pattern.  A similar problem is faced by the TS2068 which
does not have pull-ups on all its data bus lines.  The TS2068's SCLD
peripheral ID, like the ULA ID, could therefore be a random bit
pattern.  The solution used by many is to use a 257 byte table
containing the same byte value repeated 257 times.  Then the ISR
address looked up will have the same value no matter what the
peripheral ID is.  With Sprite Pack, a good value to store is 0xf1 in
all 257 bytes of the im2 vector table.  The interrupt service routine
called will always be at 0xf1f1 no matter what the peripheral ID is. 
This kind of defeats the purpose of vectored interrupts as it is no
longer known which peripheral caused an interrupt.  Effectively, we're
left with an IM1 mode that jumps to a user-definable address rather
than the fixed 0x0038 address.  This is how most Spectrum programmers
use IM2.

All is not lost however.  The Spectrum can reap the full power of IM2
by simply not attaching offending peripherals.  The AMX mouse is an
example of an interrupting peripheral that functions in IM2.  The
TS2068 can fully use IM2 if attached IM2 peripherals pull up all the
data bus lines.
"

I've since had a look at the Kempston joystick schematic and it
doesn't look like it actually does interfere with correct IM2
operation.  It may have gotten a bad rap.


From the hardware point of view, IM2 peripherals are prioritized using
a daisy chain of signals IEO (interrupt enable out, active high) and
IEI (interrupt enable in, active high).  The highest priority
peripheral has its IEI attached to +5V.  Its IEO is attached to the
next peripheral's IEI.  That peripheral's IEO is attached to the
next's IEI, etc.  A peripheral knows that it has high enough priority
to interrupt if its own IEI is high.  If it wanted to interrupt it
would then disable its IEO to disable all lower priority interrupters.

The main business is transacted when the cpu performs an interrupt
acknowledge cycle.  To allow the daisy chain time to settle, the
acknowledge cycle begins with /M1 going low.  While /M1 is low, IM2
peripherals are not allowed to change their interrupt request status. 
After a few cycles of /M1 being low, /IORQ goes low.  At this point
the highest priority interrupt requester (IEI = 1 and an interrupt is
desired) places its 8-bit ID on the data bus.  When /M1 and /IORQ
return inactive, this IM2 peripheral releases the /INT line so that
other higher priority peripherals can activate it.  The IM2 peripheral
keeps its IEO low so that lower interrupt priority peripherals cannot
interrupt while this IM2 peripheral's ISR runs.

Following the successful read of the peripheral's ID, the Z80 looks up
the ISR address and calls it.  The ISR address ends with the execution
of a RETI instruction.  An IM2 peripheral that has had its interrupt
acknowledged must look for this.  If its IEI is high (so that no other
higher priority interrupt's ISR is running) and a RETI is executed,
the IM2 peripheral knows its interrupt service routine has completed
execution and it resets its interrupt circuitry.

IM2 peripherals can also function correctly in IM1 mode.  In IM2 mode
the ULA can be, conceptually, the lowest priority interrupter without
any special accommodation.

There you go; not exactly trivial and you'll probably want a PLD to
implement the logic.  I wrote some Verilog a few years ago and
designed a circuit years before that to handle IM2 peripherals.  I'll
see if I can locate it for you.

line /INT is level sensitive.  A peripheral that wants to interrupt
(and has IEI high) should hold /INT low until it is acknowledged.

When the periperal's interrupt service routine has been acknowledged,
its ISR begins execution.  The peripheral keeps its IEO low to prevent
lower priority interrupters from interrupting the execution of its
ISR.  This IEO stays low until the peripheral sees a "RETI"
instruction executed with its IEI high, indicating its ISR has
completed execution (if its IEI were not high, the "RETI" would belong
to a higher priority peripheral's ISR).  Conveniently, instruction
fetch cycles are distinguished from ordinary memory read cycles by the
assertion of the M1 signal, which also serves the purpose of settling
and freezing the state of the IEI/IEO daisy chain.

Yeah, that's not actually correct.  In the version I've scanned, the
state of /INT is marked with dashes to indicate don't care except on
the rising edge of the last T state in the last machine cycle of an
instruction.  This just means the cpu is paying attention to /INT at
this time -- if the peripheral doesn't have /INT low at this moment,
tough luck in having the cpu notice your interrupt.

On /NMI you can just pulse the line because it's edge triggered (the
z80 has an internal flip-flop that will take note of the edge, and the
state of this flip-flop is what is sampled by the cpu).

Since the maximum Z80 instruction is 24 cycles or so long, you could
hold /INT low for about 48 cycles and then you could be pretty sure
that the cpu will notice the interrupt.  However, as Mike pointed out,
if the associated ISR is really short, this single long pulse on /INT
could cause a double interrupt.

Worse, though, is that this method ignores the possibility that:
1.  The user could have disabled interrupts for a short time for a
timing critical piece of code.  During this time the /INT pulse could
have come and gone, being ignored by the cpu, when in fact the
intention is to delay acknowledgement of the interrupt.
2.  There could be another bus master in the system (a DMA controller)
that has control of the buses when the interrupt occurs (the bus
master should ignore interrupts and the cpu should acknowledge them
when it regains control of the system).

If you check out page 64, step 2 of the pdf I scanned, you'll also see
the instructions for deasserting /INT during the acknowledge cycle.
