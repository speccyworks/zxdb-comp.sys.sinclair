AIR files created with RealSpectrum work also with future releases of the
emulator, including the Linux and Windows versions currently under
development. Personally, I'd love to see a comprehensive archive with AIR
files for all the best Spectrum games! :)

> http://www.the-tipshop.co.uk/hoh128.air

AIR files store an exact recording of the keyboard and joystick input,
preserving their exact temporal sequence. Therefore, if you want to watch
exactly the same game you recorded, you must obviousely start playing the
AIR from the same point where the recording begun, otherwise the keypresses
will probably have no meaning. Just imagine what would happen if you play
the AIR file of HOH when the Spectrum is running a different game, e.g.
Arkanoid: totally nonsense. Or if you started to record the AIR from the
main menu of HOH and you begin to replay it from the hi-scores screen.
Playing AIR files is like mixing audio and video in a movie: make sure that
sound effects and speech are in sync with the respective pictures, otherwise
the result is horrible :-)
Using snapshots (i.e. the Snapshot Sync option) is the safest method to
ensure that everything matches (and in this case use the same snapshot), but
it is not the only one. For example, let's suppose that you started to
record at the joystick selection menu which appears as soon as the game
starts; then, you may include a small note with the AIR where you say to
load HOH (in whatever form, tape or snapshot) and start the AIR playback
when the joystick menu arrives.
We recommend the good practice of testing the playback yourself before
spreading the AIR, and include some quick instructions if necessary.
Besides, with certain games like Batman the Movie and Ghouls'n'Ghosts you
are forced to use snapshots (check the "Snapshot Sync" paragraph into the
manual of RealSpectrum to see why).

Although we have tried to make the AIR system as easy as possible, there are
several tricks involved into action recording that can only be understood
with practice. If you have any doubts, do some experiments and see if it
works.

finish HOH and I couldn't stand giving up at the end! :-)

Please feel free to ask us more questions concerning AIR files, if you have
any doubts!

I don't think that is how it's done - the AIR file is a pretty universal

> Or it may just capture input events and
> the times between keypresses,* but I'm not sure that would be easily

Yeah - just do a "Record Mode" - ie, when a user event is triggered, then
store it and the time it occurred (sp?) - probably best to store the
emulator's internal time, rather than the actual system time. If we're going
to do a spectrum-specific one then the internal spectrum clock would do, I
expect.

proposal (and there's loads of reasons why this shouldn't be done like
this):

When the user chooses to start a recording, the emulator should perform a
cold-reset, and either a LOAD"" or [RETURN] depending on the hardware
specified by the user. Once the game has loaded, then recording commences
from when the user stops the tape (or it auto-stops, or the user presses a
particular key-combo) - logging the time (in the emulator) that it started.
Then continue until the user presses a key-combo or whatever.

This way, everyone gets to see the AIR file in action - and as we're
thinking of attaching to TZX Files, then everyone should have the same
copy - let's make them the property of the TZX Vault, for simplicity and
distributability. TZXs already have a small section for putting pokes into
them for later use by the user, so why not AIR (or IZX or whatever) files
too?

TZX Vault updates regularly replace old TZXs with newer, more accurate ones,
so as the IZX files come in, they can be re-issued as IZX compatibles.

That's a damned fine idea there, Mr. Young.

Firstly, you need a user to type LOAD ""<enter> (or just press <enter>)
after reset. This isn't going to be a T-state accurate operation.

Secondly, different emulators will take different numbers of T-states to
load a given game - the most obvious difference I can see here is
contended memory emulation, which whilst this will produce only a small
drift for each frame, will add to to a significant number of T-states
over the course of a game. It may be possible to produce a (game
recording) file format which (mostly) works around this problem, but I
can see this going horribly wrong.

Thirdly, is the ULA's T-state count reset when the Spectrum is reset? If
not, interrupts will occur at a different point in the cycle, which
produces yet another problem you're going to have to deal with.

Basically, if you want a `snapshot' of the Spectrum's memory, I think
you're going to have to use (shock horror!) a snapshot format, not a
tape format. Even so, I'm not sure this is perfect -- there have been
known problems in the past with the same information in snapshots being
interpreted differently by different emulators (in particular, is
snapshot saved before or after the R register is incremented? On a real
Spectrum, this is an irrelevant question as you can't do anything in
that time span, but if you snapshot it on an emulator, you can get an
off by one error).

No; adding to that the state of the Z80 and the ULA and you'll be pretty
close to there.

>In layman's terms, what is the T-state?

A T-state is the indivisible unit of time used by the Z80; nothing can
happen on a timescale shorter than a T-state. For the 48K machine, you
get 3.5 million T-states in a second, or 69888 in a frame.

The important thing about the T-state count is that an interrupt happens
every 69888 T-states after the Speccy is switched on, no matter what you
do to it in the meantime[1]. Hence having a count of how many T-states
have elapsed since the last interrupt is pretty crucial for emulators,
and (I think) important for any recording file format as well, as having
an interrupt occur at the wrong time could break things up.

>is it a register (or some other variable stored in the processor itself
>and not in ROM or RAM)?

It's in the ULA rather than the processor, but you've got the basic
idea.

>Why not record those, too?

Most snapshot formats do (including .z80).

2001-08-31 18:53:47 Chris Cowley Re: Fresh AIR? (Re: Head Over Heels AIR file)
On Fri, 31 Aug 2001 18:27:07 +0100, Nick Humphries
<…@…> wrote:

I haven't been paying attention to the actual discussion about recording
input events, but I can answer these questions for you...

>If you took a snapshot of both the RAM and ROM, would that be a complete
>representation of the current state of the Speccy?

Nope. You need to record all of the CPU registers too and, for a 128K
speccy, the state of the AY-8912 registers and the contents of the
paged-out (i.e. not currently addressable) banks of RAM too, plus the
current video scan position if you want to be really accurate.

>In layman's terms, what is the T-state? is it a register (or some other
>variable stored in the processor itself and not in ROM or RAM)? Why not record
>those, too?

Slightly simplified:-

T-States are CPU clock 'ticks'. In a 48K speccy, there are a total of
69,888 clock ticks for each interrupt, and there are 50 interrupts per
second (or thereabouts, but that's a whole other issue):-

It takes to a fixed number of these 'clock ticks' to execute each
different Z80 instruction (for example, "XOR A" uses 4 t-states while
"LD A,(nn)" takes 13), but this is all further complicated by the fact
the bottom 16K of RAM is shared between the CPU and the ULA which
handles the video display -- and this is what is meant by "contended
memory".

If the CPU executes a "LD A,(nn)" on the bottom 16K of RAM at the same
time the ULA is updating the video, then the CPU has to wait until the
ULA is finished, so the instruction might take more than 13 t-states to
complete. The number of additional t-states used up depends on exactly
what bit of the video display the ULA is working on at the time.

The problem this presents with regard to recording keyboard/joystick
input is that different emulators have their own ideas about how this
contended memory works (to the point that some emulators don't bother
emulating memory contention at all). So if your input file says "the
user held down the 'q' key for 4982 t-states, then released it for 232
t-states, then held the 'p' key down for 1924 t-states", those key
presses would occur at subtely different times depending on the emulator
you're using. Over the course of an hour or two, the drift in t-states
between two different emulators might add up to two or three seconds, so
an input file that successfully completes a game on one emulator might
cause the player to jump into the arms of a bug-eyed monster on another.

Not an easy problem to solve.

>seconds of *actual* time, on the assumption that the emulator is
>running at 100% speed (emulators not running at 100% speed should
>employ tactics such as working out the emulated time difference). 

Won't work. "100% speed" is another way of saying "the emulator is
processing the t-states for all operations with 100% accuracy", which in
practice very rarely happens. This is what I was trying to get at in my
previous post; if you run the same snapshot in two different emulators
side by side for a couple of hours, the chances will be quite high that
they end up out of synch to some degree or other. Perhaps only a second
or half-a-second, but that's more than enough to throw the timing for
lots of arcade games out of the window.

Given that lots of games take a while to complete, the chances of two
emulators having counted exactly the same number of t-states (or running
for exactly the same amount of time at "100% speed") is unlikely. If all
emulators counted the same number of t-states for every Z80 instruction
(including the instructions not documented by Zilog) and they all
emulated the ULA and contended memory in exactly the same way, then
there wouldn't be a problem. But, alas, they don't. So there is.

>There is the possibility that this will not be accurate enough, but at
>least actual time (or even computer time) does not drift significantly
>under normal circumstances.

It will drift significantly. I guarantee it. Much more so than relying
on counting t-states because not all emulators use timers with
high-enough resolution to be millisecond-perfect over a number of hours.
For that matter, as I understand it (but I'm not a hardware person at
all), I believe you'll find that different speccies (real ones, not
emulated) run at slightly different speeds depending on the vagaries of
the power supply involved. So measuring 'real' time is a definite
non-starter over extended periods of time.

>Then again, you're probably better off working with t-states.

As far as I can see, counting t-states between events is the most
accurate option available. But it won't produce exactly the same results
in all emulators. Maybe the differences will be so small as not to cause
too many problems in most circumstances though, I've no idea...
