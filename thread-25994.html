2002-08-22 19:28:38 Andrew Owen 
Hi all,

As I'm sure you know by now, I have worked very hard for a very long time
on this project but I haven't done any work on it since February and I
don't think I can ever finish it by myself. So, having done the ground
work, I'm making the project open source. What that means is I'm still in
control of the project, but the code is now freely(ish) available, and
improvements will be included in future official releases at my
discretion. If you want a copy of the (mostly) commented source code in
TASM/ZASM compatible format then email me. That way I can keep track of
who is working on the code. The source is for the earlier 0.69T
non-release but except for the copyright message it compiles exactly the
same binary as the 0.70 public release which is available as an .ips file
from http://www.worldofspectrum.org/sinclairbasic/

-- 
I'm really here. You're not imagining it.

Hi,

You carbon copied me the binary and source back in January and like
Chris I couldn't get the binary to work so never looked at the source
file. I just had a peek last night.

The problem could be that it is set up for a rather lenient assembler 
under MacOs and needs something with discipline like the DOS/Unix
Telemark one that I use.

In your tokenizer section there is the instruction 
EX IX,(SP)  which Zilog insist should be  EX (SP),IX 
Also,
ADD B       which should be               ADD A,B  (twice)  
ADD 8       which should be               ADD A,8  (once)

Your assembler insists on colons at the end of labels, and I altered the 
base file to suit this, but it also allows colons in for example
PROG: equ  $5C53
which is plain wrong.
I also had to define a lower case equ 

Your assembler may not be laying down the bytes you think it is
disguised by the fact that you instruct it to always build a 16K file.

Making the above changes, I ended up with a ROM file with a cute
tokenizer that gave PRINT INT(.5 + .5) correctly.

Making these changes would make the file more acceptable among the
Unix/DOS community.

No but that is not an endorsement. :-) It just means I haven't checked
anything. As you know I think the line number thing is a retrograde
step. However if I should come across something, I will let you know.
Once I get time, I am planning my own "Sea Change" ROM.

The secret is to test every little change as it is made.

I believe you have abandoned the 128K ROMs but there is a bug in some
that is due to a mistake in "The canonical list of +3 oddities" which
is, in turn, due to an error in "The Complete Spectrum ROM Disassembly".

The latter has 

2096 INPUT-1    LD      (DF-SZ),+01

which actually disassembles as 

2096 INPUT-1    LD      (TVFLAG),+01

A comparison with the 128K INPUT routine and "The Book" produced the
discrepancy in the canonical list which is actually OK.

219C: A "LD (TVFLAG),1" should probably be "LD (DFSZ),1" (harmless).

So if a ROM makes the change then there will be two blank lines instead
of one between the lower input window and the upper screen window.

Furthermore, INPUT can continue until the upper window is obliterated
altogether, whereas at least one line should always show.

set up. You have to muck about with more things to make the range 0-9999
across the ROM than you do 0-16383. And since most people number in 10s

range will still execute on the original ROM, which was my main
consideration in deciding whether to do it or not.
