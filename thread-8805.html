                         ZX Spectrum Tape file format
                        ------------------------------
                                revision 0.0
                       Still in Development - version 9

  This format lets you preserve all (hopefully) of the tapes with turbo or
custom loading routines. Even though some of the newest and 'smarter' emulators
can find most of the info about the loader from the code itself, this cannot be
possible if you want to replay the file to the good old real spectrum. And with
all this information in the file the emulators don't have to bother with finding
out the baud rate and other things.

  There were three suggestions for the preferred 3 letter filename extension:
(The number on the right is how many people voted for that extension)
.SPT (SpectrumTape)              4
.TZX (Tape for ZX)               9
.TPE (as TaPE)                   2
.TPX (TaPe eXtension)            1
.MST (Multispeed Sinclair Tape)  1
.ZAT (zed - ay-tee)              1
.TST (Turbo Spectrum Tape)       1

.ZXT is already used for another file type. Please tell me which one is your
favorite or suggest some other... The one most favorite will be used in the
final version ;)

  The file is identified with the first 8 bytes being 'ZXTape!' plus EndOfFile
byte 26 (1A hex).
  After these 8 bytes the two bytes with the Major and Minor Revision number
follow. First byte is Major revision number - the program must be able to handle
at least this revision number or earlier to use the file.
The Second byte is Minor revison number - if the program can handle only formats
with lower Minor revision number than the one in the file then some information
could not be interpreted (but that info should not be so important...).

  Then the body follows which is devised from blocks. Each block is identified
with its ID byte followed by its body. There are currently 11 types of blocks.

So the file structure is :  'ZXTape!' 0x1A MajR MinR ID1 Body1 ID2 Body2 ...
                             0        7    8    9    A   ...

- The Two-Byte values are always stored LSB (Least Significant Byte) First.
- The bit order in a byte is  : 7 6 5 4 3 2 1 0
                and in a word : first  byte (LSB) :  7  6  5  4  3  2  1  0
   (word == short == 2 bytes) : second byte (MSB) : 15 14 13 12 11 10  9  8
  All unused bits should be Unset - 0 !
- The timings are given in Z80 clock ticks (T states) unless otherwise stated.
  1 T state = 1sec/3500000
- The values in the tables mean : Offset (in HEX bytes), Length (1-byte, 2-word)
- You might interpret full-period as one pulse (----____ or ____----) and
  half-period as only one half of the pulse (---- or ____).
- The values in brackets [] are the fefault values of Spectrum ROM load/save
  routines - they should be used for all Standard loading blocks.
  These values are in Decimal format. (All other values (IDs,...) are in HEX)
- If there is NO pause between two data blocks then the second one should
  follow immediately after first one (no T-states should be between them).

These are the possible blocks :


ID : 10  -  Normal Speed Data Block (as in .TAP files)
-------
          This block must be replayed with the Standard ROM Values for all
          Loading Speed variables (values in brackets []). If you know the
          default values for ZX-81 ROM save/load routine then please email me.
          This block can be used for the ROM loading routines AND for custom
          loading routines that use the same timings as ROM ones do.

00 2  Pause After this block in miliseconds (ms)                         [1000]
03 2  Length of DATA that follows
04 x  DATA, as in .TAP File

ID : 11  -  Custom Loading Data Block
-------
          This block is very similar to the normal .TAP block but with some
          additional Info on the timings and other important differences.

00 2  Length of PILOT half-period                                        [2168]
02 2  Length of SYNC First half-period                                    [735]
04 2  Length of SYNC Second half-period                                   [667]
06 2  Length of ZERO bit half-period                                      [855]
08 2  Length of ONE bit half-period                                      [1710]
0A 2  Length of PILOT tone (in PILOT half-periods)     [8064 Header, 3220 Data]
0C 1  Used bits in LAST Byte (other bits should be 0)                       [8]
      i.e. if this is 6 then the bits (x) used in LAST byte are: xxxxxx00
0D 1  Copy Protection Scheme

        If the block is saved using one of many copy protection schemes then
        use this byte to specify which one. Note that some schemes use default
        half-periods for some values and you should use the default ones if they
        have value of 0 above. Unfortunetly I don't have much info on this
        subject... if you have ANY more info than I, then PLEASE contact me!

        All Protection schemes are described at the end of the document.

        Here are the possible values:
          00 - No Copy Protection Scheme used
          01 - SpeedLock 1

0E 2  Pause After this block in miliseconds (ms)                         [1000]
10 3  Length of DATA that follows (Least Significant Byte First)
13 x  DATA, the bits are saved MSb (Most Significant bit) first - as in Real ZX

      NOTE: If any SYNC half-period is 0 then the pulse amplitude must not
            change at that position ! (so the loaders with only one SYNC
            half-period can be supported... (this is for blocks with NO
            protection scheme))

ID : 12  -  Direct Recording
-------
          This block is used for tapes which have some parts in such format that
          the Custom Loading block cannot be used. This is NOT like the .VOC
          file, since the information is much more compact. Each Sample value is
          represented by One BIT only (0 if it is LOW  and  1 if it is HIGH)
          which means that the block will be atleast 8 times smaller as the .VOC
          file would be. PLEASE use this block ONLY if you cannot use the
          Custom block!!!

00 2  Sampling Frequency in Hz (Please use only frequencies of upto 44100 Hz !)
02 2  Pause After this block in miliseconds (ms)
04 4  Data Length (Least Significant Byte First)
08 x  Data... each BIT represents a state on the EAR port,
      Most Significant Bit is played First !

ID : 20  -  Pause (with an optional message) or Stop the Tape command
-------
          If the Value is 0 then the Pause should be Indefinite and
                            the Emulator or Utility should STOP THE TAPE.
          If the message length is 0, no message is displayed.  If it is
nonzero,
          then a message is displayed for the duration of the pause.
          When a message is displayed, the emulator stops emulating the program
          for the duration of the pause.  Only pause blocks without messages
          are actual pauses as far as the emulated program is concerned.
          If the Pause is indefinite AND there is a message then the emulator
          should wait for a key press to end the message and after the keypress
          the tape should continue running.

00 2  Value of the pause in miliseconds (ms)
02 1  Length of the message (if 0 then NO message)
03 x  Message that should be displayed (in ASCII)  Suggested format: stick to
      a maximum of 30 chars per line.  Use single 0x0D (13 decimal) to
      separate lines.  Stick to a maximum of 8 lines.  If you do not obey
      these rules, emulators may display your message in any way they like!

ID : 21  -  Jump To Block
-------
          This block will enable you to jump from one block to another block in
          the file. i.e. if you want to skip some blocks or go back some blocks
          then this is now possible. The value is 2-byte SIGNED RELATIVE offset.
          Which means if the value is 2 then you jump 2 blocks ahead. If it is
          -3 you jump 3 blocks back. Simple as possible :)

00 2  Relative Offset : In Binary Complement, MSbit is the sign (FFFF = -1)
      (this is Offset in BLOCKS, NOT Bytes)

ID : 22  - BEEP block
-------
          This block allows you to make the beeps between the blocks or after
          the game. Sometimes the games on speccy tapes would make these noises.
          This is very much like BEEP Duration,Pitch  in ZX BASIC.
          The Frequency of the tone is calculated with the following formula:
            f = 440+2^((Pitch/100-9)/12)  [Hz]

00 1  Duration of the tone in tenth of seconds (1s/10)
01 2  Pitch (SIGNED WORD) - the number format is the same as in 'Jump To Block'
      Pitch of the played tone multiplied by 10, given in semitones above middle
      C, using negative numbers for notes below middle C (exactly the same
      definition as in BEEP command)
        E.g. if Duration=5 and Pitch=95 then it is the same as BEEP 0.5, 9.5
03 2  Pause after the Beep in miliseconds (ms)

ID : 30  -  Text Description
-------
          The description can be upto 255 characters long but please keep
          it down to about 30 so the programs can show it in one line !
          This is ment to identify parts of the tape, so you know where
          level 1 starts, where to rewind when you lose all the lives, etc.
          Please use 'Archive Info' block for Title, Authors, Publisher,...
          This description is not guaranteed to be shown during tape playing,
          but can be read while browsing the tape or changing the tape pointer.

00 1  Length of the Text
01 x  Text in ASCII

ID : 31  -  Archive Info
-------
          Use this block in the beginning of the tape to identify the Title of
          the game, Author, Publisher, Year of publication, etc. This block is
          build in a way that future expansions are easily possible. The block
          consists of Texts. Each text has its Identification Number (which
          tells us what the text means) and then the ASCII text. To make it
          possible to skip this block, if needed, the length of the WHOLE block
          is on the start of it. Note: The information about what hardware the
          tape uses is in the 'Hardware Type' block, so no need for it here.

00 2  Length of the block (without this two bytes)
02 1  Number of Texts
03 x  Here are all the texts in the format:
        00 1  Text Identification byte:  00 - Full Title
                                         01 - Software House / Publisher
                                         02 - Author(s)
                                         03 - Year of Publication
                                         FF - Comment(s)
        01 1  Length of the Text
        02 x  Text in ASCII format
        ....  Next Text

ID : 32  -  Hardware Type
-------
          This selects what hardware the programs on this tape use.
          Please include only Machines/Hardware for which you are 100% sure that
          it either runs (or not runs) on that machine/hardware or you know it
          uses (or not uses) the hardware or special features of that machine!
          NOTE: If the tape runs only on ZX-81 then there is no need to put all
                the other Machines to DOESN'T RUN (and vice versa)! I think
                the emulators and utilities can be so smart to detect that :)

00 1  Number of Machines/Hardware for which Info exists
01 x  List of Machines/Hardware :
      00 1  Hardware TYPE
      01 1  Identification ID of Machine/Hardware

               The list of all Hardware Types and Identifications is getting
               quite Large and it is moved to the end of the format description!

      02 1  Value : 00 - The tape RUNS on this machine (or with this Hardware),
                         but it is not sure whether it uses the hardware or
                         special features of the machine.
                    01 - The tape USES the hardware or special features of the
                         machine. (like 128k Memory or AY Sound on 128k ZXs)
                    02 - The tape RUNS but it DOESN'T use the hardware or
                         special features of the machine.
                    03 - The tape DOESN'T RUN on this machine
                         (or with this Hardware)
      ....  Next Machine/Hardware Info

ID : 33  -  Emulation Info
-------
          This is a special block that would normally be generated only by
          Emulators. For now it contains info on everything I could find that
          other formats support. Please inform me of any additions/corrections
          since this is a very important part for emulators. Those bits that
          are not used by the emulator that stored the info, should be left at
          the DEFAULT values.

00 2  General Emulation Flags
        Bit  0 : R-register emulation                                       [1]
             1 : LDIR emulation                                             [1]
             2 : High Resolution Color emulation with True Interrupt Freq.  [1]
           3,4 : Video Synchronisation : 1=High, 3=Low, 0,2=Normal          [0]
             5 : Fast Loading when ROM load routine is used                 [1]
             6 : Border emulation                                           [1]
             7 : Screen Refresh mode (1: ON, 0: OFF)                        [1]
             8 : Start Playing the tape Immediately                         [0]
                 If this is 0 then the emulator should only load the info
                 blocks and WAIT when it encounters first DATA block
             9 : Auto type LOAD"" or press  when in 128k mode [0]
02 1  Screen Refresh Delay : 1 - 255 (Interrupts between refreshes)         [1]
      (used when Screen Refresh Mode in General Emul. Flags is ON)
03 2  Interrupt Frequency  : 0 - 999 Hz                                    [50]

05 3  Reserved for future expansion (Should be 0)

ID : 34  -  Custom Info block
-------
          This block can be used to save ANY information you want. i.e. if some
          utility desires to write some stuff into the tape file then this block
          should be used. it can be upto 65535 bytes long and it can contain
          ANYTHING ... for instance : If the emulator has some settings that
          are not described in the 'Emulation Info' or someone wants to make
          a block containing POKEs or whatever then they can use this for it.
          Ofcourse some of these blocks can be standardised in the future ...

00 F  Identification String (in ASCII)
10 2  Length of the info that follows
12 x  Custom Info

ID : 40  -  Snapshot Block
-------
          This would enable one to snapshot the game at the start and still
          have all the TAPE blocks (for next levels, etc.) in the SAME file.
          I don't know if this is a good idea or not, it was suggested and I
          have to put it in to see what you mean. The preffered formats are
          Z80 and SNA since they are widely used.

00 1  Snapshot Type : 00 - Z80      (Z80 Emulator, Warajevo,...)
                      01 - SNA      (JPP, Amiga Spectrum Emulator,...)
                      02 - SNP      (Didaktik disk snapshot)
                      03 - SIT      (Sinclair 2.0 by Pedro Salaz)
                      04 - SP       (Sinclair 0.99 by Pedro Gimeno)
                      05 - PRG      (Irish SPECEM emulator)
                      06 - SEM      (German SPCEMU-G)
                      07 - SNA-128  (Russian SP-UKV)
                      08 - RAW      (SAVE "FILE" CODE 16384,49152)
                      09 - SNX      (from Atari)
                      0A - ACH      (from Archimedes and Risc PC)
01 3  Snapshot Length (Least Significant Byte First)
04 x  Snapshot itself

ID : 5A (90 dec, ASCII letter 'Z')
-------
          This is a block that would be generated if you merged two ZX Tape
          files together. It is here so you can easily copy the files together
          and use them. Ofcourse this  means that resulting file would be 8
          bytes longer than if this block was not used. All you have to
          do if you encounter this block ID is to skip next 9 bytes. Please, if
          you can don't merge two files together this way, use a utility that
          will let you do that without having this extra block.

00 9  'XTape!' 0x1A MajR MinR  Just skip these 9 bytes and you will end up on
                               the next ID.



                              PROTECTION SCHEMES
                             --------------------

01 - SPEEDLOCK 1 (Atleast I think this is version 1)
    -------------

  You can identify this protection scheme by its 'clicking' Pilot tone. If you
look into the loader you will see this message: 'Protected by SPEEDLOCK' and
some bytes later: 'SPEEDLOCK Protection System. DJL Software & D. Aubrey Jones
1984 - Tel: 0793 72317 * Government Health Warning - Attempting to crack
SPEEDLOCK can damage your sanity!'.
  Basically speedlock is protected with the clicking Pilot tone, not-standard
SYNC pulse and higher loading speed. Normally there are two Speedlocked blocks
in the file. If you try to convert them with the normal algorythm you will get
a block with a very small pilot tone (around 216 half-periods), almost standard
SYNC and the data full of Zeroes. But since I haven't got it working yet this
information might be WRONG.

  The PILOT tone starts off with 219 half-periods with normal timing then the
'click' signal appears, which is 3 half-periods of half the size of Pilot HP
and then this is repeated 30 times. After this there are 216 normal HPs and
then the SYNC tone which is built from 3 half-periods, first one is 1.8* length
of Pilot HP, second one is the same length, third one is half the length of
Pilot HP. After this the data follows (turbo saved). This is how it looks like:

___---___--- ... ___---_-_ ... ---___--- ... ___---___-----___-__--__--_-_- ...
|_________ ___________|_ _|____________ _____________|____ ____|________ __ ...
          V             V              V                  V             V
   219 * [2168]    3 * [1084]      216 * [2168]         SYNC :	       DATA
|____________ ____________|                    [3852],[2168],[1084]
             V
          31 Times
|________________________ ___________________________|____ ____|________ __ ...
                         V                                V             V
                    PILOT Tone                          SYNC           DATA

  I am not sure if the Loading speed is always the same, so it should be read
from the Bit-0 and Bit-1 half-periods in the file. Other values seem to be OK.
(these values were gathered with experimenting, they are NOT gathered from the
code... if someone has more accurate values for any of the protection schemes
then please contact me).
  I could convert the Speedlock 1 blocks succesfully. Unfortunetly I could not
replay them properly back. This is VERY odd since the resulting block is almost
100% the same as the original :( The problem might be that the block is not
properly finished... but whatever I tried didn't work :(

Here are my remarks and suggestions for the new tape format.  It is a
bit longish, I hope you'll be patient with me....

-----------------------

I have a few suggestions in order 
to make the format more 'horizontal', more uniform, as opposed to it being
a bag of different types of blocks.  I have a suggestion for a new small and 
versatily 'sound block', which encompasses the BEEP block and the protection 
scheme and is easier to implement.  Using this block, by the way, we could 
change the format of the 'ordinary' tap block and the 'custom' tap block, to 
unite them into a single other block.  Well, you will understand what I mean 
when I get to it.  So here goes:

-----------------------

We want a format that has the following characteristics:

1. It should be versatile, to be able to hold ordinary tapes as well as
   various turbosaved variants.
2. It should store tapes as short as possible (within reasonable limits),
   so no direct sample file in cases where it can be avoided
3. It should be easily extendible (the format, that is), to incorporate 
   information that we do not think of now but want to include later on.
   This should be possible in such a way that old version of programs can
   easily ignore the new information.
4. The format should use as little different sub-formats as possible, to
   make implementation easy and less error prone.
5. The format should include a detailed specification how an emulator is
   to respond to it, and which information can be ignored.

-----------------------

In order to achieve 1 without going against 4, I propose the following 
block types.

-----------------------

ID: (range 10-1f) - Pure tone

00 2	Length of pulse in T states
02 2	Number of pulses ("half-periods") (may be odd)



ID: (range 10-1f) - Single pulse (i.e. one edge or "half-period", not two)

00 2	Length of pulse in T states



ID: (range 10-1f) - Data pulses

00 3	Total length of block excluding this length field 
03 1    Bit 0-3: number of significant bits in last byte (1-8);
        Bit 4: Set if this is a 'browse point'
        Bit 5-7: Reserved (zero)
06 2    Length of zero bit half period in T states
08 2    Length of one  bit half period in T states
0A x    Data bits

Field 03 should be less than or equal to 8 times (field 00 minus 7)



ID: (range 10-1f) - Direct recording

00 3  Total length of block excluding this length field
03 2  Bit 0-11:  Number of T states per sample (max 4095 = 1.17 ms)
      Bit 12: Set if this is a 'browse point'
      bit 13-15: Reserved (zero)
05 x  Data... each BIT represents a state on the EAR port.  A zero
      signifies the same level as a Pause block, so data levels do not
      depend on the previous level.  The levels of blocks after a
      Direct Recording block depend on the last bit of the Direct
      Recording block, except for Pause and Direct Recording blocks.
      The last level of the DR block equals the first pulse level of
      a subsequent block, just as in the case of a zero-level pause block.
      (See remark 3 below)



ID: (range 10-1f) - Silence

00 2	Length of silence (output level = 0) in ms

-------------------------------------------------------------------

Remarks:

1. Note that I changed 'sample frequency' into '# of T states per sample'
   in the 'direct recording' block, and removed the 'pause length' field
2. When browsing, not all blocks should be shown, at least not by default.
   The 'browse point' bit in 'Data Pulses' block is normally set, and
   the block should be shown when browsing (with features like if the length
   is 19 (?) and flag byte is 0, then assume it is a header and show the
   contents, etc., up to the emulator programmer).  The use of the bit is
   that maybe a single block consists of a number of small data blocks and
   pure tones, and not all data blocks should then be browse points.
3. All pulses from the first three blocks generate a 'toggle' of the output
   level.  The Silence block generates a 0 level output always, AND resets
   the toggle.  The first non-silence block should START with a 0, then 1,
   etc.  This is to ensure that if you use an even number of pilot 
   half-periods, two sync pulses and a data block, the last pulse of the
   data block is high, and the transition to 'pause' gives the last edge,
   which is crucial to correct loading.  Therefore a data block should
   normally not be the last block of a .TZX file, except if it is known
   that actual loading terminates before the last bit on the tape.
4. These four blocks are building blocks for literally any tape format,
   and secondly the overhead for using these to make normal tape files is
   only slight.
5. I think I am in favour of including a 'normal .TAP block' block, so that
   only custom blocks have to be 'written out' in full.  This saves a few
   bytes per standard block, but it might be worth the trouble.
6. Above four blocks (or five, if 'normal .TAP block' is included too)
   make the normal 'custom block' unnecessary.  Relative to this, the proposed
   four blocks take up only a few more bytes, and I think the added
   versatility more than make up for this.
7. I am very much opposed to the 'copy protection scheme' byte.  PLEASE
   do not include this!  A format should be versatile and simple, not
   specific!  Adding another copy protection scheme involves coding
   a new piece of program in each and every emulator, and this is bound
   to give problems with emulators that are not updated anymore, etc.
8. I think it is a good idea to include the known timings of various
   copy protection schemes in the DESCRIPTION of the format, so that
   hackers can use it to transform tapes in the .TZX format.  But it should
   not be necessary that emulators know about the detailed timings of the
   various schemes, at least that's how I feel about it.
9. The 'single pulse' block is actually redundant.  Tape files get a little
   larger when the 'single pulse' block is not implemented, but I would not
   mind.  The standard format has two sync pulses of unequal length, but
   the loading routine is not at all sensitive to this.  In the TAP2VOC
   utility I use very rough timing constants for the pilot tone and sync
   pulses, and equal-time sync pulses, and this works very well.  I am
   slightly biased in favour of not implementing the 'single pulse' block,
   but for very involved formats this may lead to increased tape files,
   so I am not sure about this.
