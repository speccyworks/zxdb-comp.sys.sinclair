Hello,

I am now heavily working on version 0.30 of the signal extension.

In addition to the add-ons that became necessary to handle emulated
system calls like read(), write() there will also be some changes to
to simplify interfacing with the signal extension that will make it 
better usable from threads. 
As a side effect these changes will also reduce the amount of global 
variables which could help the shared libraries.


The conclusion is that: if you are currently trying to figure out how
to init and install '%CSG' handlers for use with threads or from assembly,
you should probably wait for the 0.30 version where this can be done
automatically.

Bye

The explanation of what the signal extension does is quite simple if you
know what signals do - it just implements them for QDOS.

Signals in turn are used for nearly anything you can imagine, beginning
with trapping exceptions like BUS errors, SEGViolation, division by zero
and FPU exceptions,...
then they are also used for comunication between processes, asynchronous io,
timers, debugging, window managment...
and lust not least just to kill processes.

How do signals work? Well the process that wishes to handle a signal
defines a handler for it by calling sigaction().
Some signals are trigered by the OS, others may be sent by some process
using kill().
Once the signal is trigered (and is not blocked or ignored) it acts
[strongly simplified] like an hardware interrupt: the process gets
interrupted, its context is saved on the stack, and the handler routine
previously defined by sigaction is called.

The nice thing with signals is that they can also interrupt many system
calls that would otherwise hang forever or they can be used to escape
endless loops - many interpreter use them implement some kind of 'break'
