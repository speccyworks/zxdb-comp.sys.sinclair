I have now added to my "Build your own ZX80" page an NMI generator circuit 
which I have designed (with some help from Wilf Rigter and Doug Duchene). This 
is a complete stand-alone circuit which can be used to "upgrade" the ZX80 
circuit to a fully blown ZX81 with SLOW and FAST modes capable of playing 
games and software written for a ZX81. The difference between this approach 
and the original ZX81 is that it uses off-the-shelf components so there is no 
need for a ULA! I must admit it has been a very educational experience and I 
hope others will feel the same way.

The site is www.babytalk.demon.co.uk/zx80/zx80.html

This page details how to build your own ZX80 along with a link near the top of 
it to the NMI generator page. This is a fully working design. Also on th ZX80 
page is a circuit for the ZX80 (I am STILL in the process of making it a bit 
clearer), ROM images, component lists and building details.

I must stress this is not for a beginner to electronics as there is quite a 
lot of soldering involved.

Any comments or suggestions welcome.

Enjoy!

Grant.

Hello Sinclair Fans,

The ZX81 has been reborn in discrete form as the ZX97!

This project to build an enhanced, low power discrete logic version
of the ZX81 has reached a critical stage: freezing the basic design
in order to lay out the PCB. The ZX97 prototype has been tested for
a while now and seems to work fine. I had to mop up a few bugs like
the crazy FAST mode and the jumpy keyboard and I added a few 
modifications to use more readily available components (ie 74LS245 vs 
74LS257). The design is still open to participation, suggestions, 
comments, and criticism for a few more weekends so let's hear from you.

Just to remind you what we are aiming for: the ZX97 is functionally
equivalent to a ZX81 with 32K of RAM and 32K of EPROM.
The ZX97 has 3 parallel bidirectional ports for high speed communication
with a PC, and controlling the world and has a "shadow" RAM (ROM overlay) for 
development of ZX81/97 operating system enhancements.

It is always possible to add more bells and whistles but one of the
design objectives is to create an enhanced ZX81 and yet use fewer chips
than the ZX80 (the ZX81 predecesor). The other objective is to use
readily available "off the shelf" chips instead of custom chips.
In the final analysis, true emulation of the ZX81 and the ability to
run all ZX81 software including various hires programs is the "proof of
the pudding" of the ZX97 design.

Attached is the latest revision which handles the keyboard and the FAST
mode correctly.

                            ZX97 (March 11)
                              WILF RIGTER
                                
The circuit is described in functional blocks as shown in FIG 1. 
The circuit details are shown in the schematic FIG 2. The critical
video timing is shown in timing diagram FIG 3.

CRYSTAL TIME BASE CIRCUIT

This circuit generates the 6.5MHz video clock, the 3.25MHz CPU clock and
the 15.75KHz horizontal clock.
The 6.5 MHz crystal clock is divided by 2 with a 74HC74 to generate the
CPU clock and the 74HC393 dual 4 bit counter together with the 74HC11
divides the CPU clock further by 207 to generate the 15.75 KHz
horizontal frequency. The 74HC08 generates 4.6 us wide SYNC/NMI pulses
which are gated by the SYNC and NMI latches before routing to the
video/sync mixer and the CPU NMI input. The counter is also held reset
during the VSYNC period to maintain synchronization in the FAST mode
between the software generated VSYNC and the hardware generated HSYNC.

NMI/SYNC LATCH

Two SR latches are used to control the flow of NMI pulses to the CPU and
SYNC pulses to the VIDEO/SYNC MIXER. The NMI latch is set with OUT FE
which gates the NMI pulses to the CPU and is reset with OUT FD.
The action of the SYNC latch is a little more complicated because it
turns off the HSYNC pulses and generates a continuous negative sync level.
The SYNC latch is set with IN FE which resets the 15.75 KHz counter and
inverts the CSYNC output and thereby starts the vertical SYNC pulse.
Any OUT command resets the latch, terminates the VSYNC pulse and enables
normal HSYNC pulses.

I/O DECODING

To maintain compatability with the ZX81 I/O port assignment, the same
incomplete I/O address decoding is used for I/O address bits 0-3.
A few 74HC32 OR gates provide the necesary logic to access the NMI and
SYNC latches. See the previous description of the NMI and SYNC latches
for details. The ZX97 keyboard interface uses the same A8-15 row scanning
as the ZX81 and the five keyboard data lines are connected to bits 0-4
of a 74LS245 tristate buffer. The output is enabled with IN FE to read
keyboard colunm data. Another 74LS245 chip is used by the "NOP" circuit
described below and is enabled whenever a character is fetched from Dfile.
A more conventional I/O decoding circuit is used to generate address DF
for the 8255 24 bit parallel interface controller. The 8255 is used as
three general purpose parallel I/O ports. Note that the 8255 defaults to
3 input ports on reset and no further initialization is required unless
you want to use ports for output. Port A is generally used as a high speed
interface to a PC printer port. The ports are access with the port number
in register B and the I/O address DF in register C. Therefore the control
register is at port 03 and the I/O PORT A-C at registers 00-02.
A typical initialization to set up  ports A and B as inputs and port C as
output requires a control word value of 93 to be written to register 03.
Port C output bits can be accessed at two different locations:
Port C output byte is PORT 02 but in addition you can reset or set
individually at PORT 03 with control word values 00 to 0F. Even values 02 to
0E reset bits 0 to 7 respectively and odd values 01 to 0F set bits 0 to 7.
The format of the control word is as follows:

Note: Typical initialization                  D7 D6 D5 D4 D3 D2 D1 D0
      for port C as output:                   \_________/ \_____/  \_/
      LD BC,03DF ; registe 03                      |         |      |
      LD A,92    ; control data                 always 0    bit #   1=on
      OUT (C),A  ; write to DF
                                 
MEMORY DECODING

Memory decoding is performed with a 74HC251 which maps the EPROM at adress
0-8K and 40K-64K. The RAM is mapped 8K-40K but the RAM segment 32-40K may
be mapped over the 0-8K area to allow installation of modified BASIC or
other operating systems by setting 8255 port C bit 7. Note that the 0-8K
EPROM segment is then remapped to 32-40K. Furthermore the 0-8K RAM is write
protected and the VIDEO pattern data continues to be supplied from the
EPROM pattern table unless the I register is changed. This allows the 1E00
to 1FFF area of the shadow RAM to be used for 512 byte of program code.
Note that the 74HC251 is enabled with MREQ and RFSH to access the video
pattern data.The bank input is included so that a bankswitch decoder can
disable the system memory decoder when accessing bank memory.

RAM and EPROM

In this revision, both RAM and EPROM are 32K byte CMOS devices.
The RAM is battery backed up and write protected in the 0-8K segment
to avoid corrupting the shadow RAM operating system from spurious writes
especially since Sinclair BASIC performs some dummy writes to locations
0000-0004.

ROW COUNTER / CHR$ LATCH

The sinclair text mode is supported with a pattern table in EPROM at address
1E00-1FFF. User Defined Graphics (UDG) RAM pattern tables are also supported.
UDGs are accessed by changing the I register to point to the new pattern
table in RAM or EPROM. One half of a 74HC393 dual hex counter is used as
a modulo 8 ROW counter which increments every HSYNC pulse and during
RFSH time it addresses the 8 rows of patterns for each character. The ROW
counter is reset with the VSYNC signal. The 74HC374 CHR$ latch is loaded with
each DFILE character code and during RFSH it is used to address the
corresponding pattern table entries. Two bits of the 374 and a 74HC125
are used  to provide tristate outputs for the ROW counter.
The I register is intialized to address the Sinclair pattern table at base
address of 1E00 during RFSH time. In order to support True High Resolution
graphics (ie WRX16) , bit 6 of the 8255 port C is used to disable the ROW
counter and CHR$ latch tristate outputs during RFSH. Pseudo Hires is
supported without any changes although UDG's and True Hires would appear
more logical choices given the ZX97 hardware features.

KEYBOARD LOGIC

The Sinclair keyboard scanning method uses A8-15 to scan keyboard rows and
5 bits of a 74LS245 to sense column data. Two other bits are used to
sense the 50/60 Hz option, and tape in.

NOP LOGIC

When a valid character is read for screen display, the NOP LOGIC (74HC138)
decodes this condition, which turns on a 74H245 buffer to force a low level
on the CPU data bus thereby tricking the Z80 into executing NOPs during DFILE
execution.

VIDEO SHIFT REGISTER/VIDEO INVERT LOGIC/VIDEO SYNC MIXER

When a valid CHR$ is fetched from DFILE, the NOP LOGIC is saved in the
NOP register (74HC74A) and is used together with the PULSE GENERATOR to
load the video shift register and the invert latch.
The video shift register is loaded with the video pattern data from RAM
or EPROM and the pixels are clocked out at 6.5 MHz.
A 74HC74 is used to capture bit 7 of each character code and load it
into the invert register at the same time as the pattern data is loaded
into the shift register. The invert register uses a AND gate with a feedback
resistor. If bit 7 of the CHR$ code is a 1 then the video serial bits are 
inverted using an XOR gate. The video is combined (mixed) with the CSYNC 
signal to produce a composite video signal suitable for connecting to a 
video monitor or RF modulator.

                       ZX97 CHARACTER DISPLAY TIMING

The Sinclair ZX97 character display hardware shown in FIG 2 generates
a standard ZX81 screen of 24 lines of 32 characters. The character
display starts when the last blank line at the top of the screen has
occurred and and the video routine jumps to the DFILE echo above 48K.
The NOP LOGIC takes control when any opcode is executed above 48K
(A14/15 high, M1 low, data bit D6 low).

In summary the video data is loaded in the following steps:

1. The CPU reads a character code from DFILE above 48K and the NOP LOGIC
   turns on the 74HC245 and forces the CPU data lines low.
2. RD loads the 8 bit character code from RAM into the 74HC374 register
   with bit D7 into the invert register and NOP into the NOP register.
   The CPU interprets the low data lines as a NOP.
4. The refresh signal provides OE for the 74HC374 and the 74HC163 ROW
   COUNTER tristate buffer, and together with the I register this
   generates the address to the pattern byte in EPROM (or UDG in RAM).
5. The pattern byte and the invert bit are loaded into the video shift
   register and the invert latch and the video is clocked out.

In SINCLAIR video the DFILE is literally executed with NOPs substituted
for each character code. Each NOP executes in 4 clock cycles at 3.2 MHz,
during which 8 pixels are clocked from the video shift register at 6.5MHz.

The detailed sequence of operations for each character byte is shown in
FIG 3. This sequence is described as follows:

1. Each displayable CHR$ code (bit 6 low) in DFILE is addressed by the
   CPU PC and decoded by the NOP LOGIC which forces the CPU data lines low.
2. On the rising edge of RD, CHR$ data (D0-5) is loaded from DFILE into the
   74HC374 together with D6-7 into 74HC74B.  On the rising edge of T3 the
   low data lines are interpreted by the CPU as a NOP instruction.
3. During T3/4, the CPU executes the Refresh cycle and ROM address lines
   are generated with I register on A9-A15, the CHR$ latch on A3-A8, and
   the ROW counter on address lines A0-A2.
4. On the rising edge of T1, pattern data from the EPROM (or RAM) is loaded
   into video shift register and 8 pixels are shifted out at 6.5MHz. If the
   invert latch was set by bit 7, then the serial video data is inverted.

The character bytes are fetched for each horizontal line and the display is
generated as follows:

   The CPU increments the program counter and fetches the next character
   code processing each displayable character as described above.
   This repeats until a HALT is fetched. HALT opcode bit 6 = 1 and is
   therefore executed (no NOP).
   The SYNC timebase generates a HSYNC pulse independend of the CPU timing
   and  the ROW counter is incremented. The halted CPU continues to execute
   NOPs, incrementing register R and samples the INT input on the rising
   edge of each T4. When A6, which is hardwired to INT, goes low during
   refresh time, (bit 6 of the R reg = 0), the Z80 executes the INT routine
   (below 32K).
   The CPU returns from INT and resumes "excution" of DFILE CHR$ codes.
   The process repeats 192 times and then INT routine returns to the main
   video routine, turns on the NMI latch and switches back to the
   application code.

   This is a short version of the ZX80/ZX81/ZX97 display system analysis
   described in more detail in the ZX81 VIDEO TUTORIAL.
