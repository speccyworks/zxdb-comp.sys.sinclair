  Well, after looking into how inadequate ( or how do you spell it :) ) the
current .TAP format is for ANY custom loading routine, I tried to come up with
a solution that would load ANY spectrum game into emulators or real spectrum
( which i prefer ). I hate those .VOC files, since they are HUGE and there is
no nice way to load them into real spectrum via SoundBlaster ( because of SB's
strange way of selecting sample rate many .VOC files that can be loaded into
emulators CANNOT be loaded back to spectrum ... ).
  I believe the implementation of the file that is described below would work
on BOTH emulators and it will ( probably ) be good for loading the file to a
real spectrum via whatever SoundCard on whatever computer.
  This is only a proposal for a file, therefore it has some still unanswered
questions in the structure... since I recieved first Turbo loading routines
and custom loaders only 2 weeks ago ( YES, i lived off pirated software back
in the eightiees ... that what Yugoslavia was back them ... noone could buy
original stuff so we had to be sattisfied with cracked games... I only saw one
turbo loading game back then - Knight Rider :) ) ...
  Now I have quite a few .VOC files that CANNOT be loaded into real spectrum
( i made a pretty good utility that loads MOST of them to the real thing, but
some turbo loaded ones cannot be loaded WITH any player for .VOC files i got ).
I am willing to make a .VOC to .??? convert utility when the .??? file
structure is defined... and ofcourse a loader to load them into real spectrum
via SoundBlaster too..

  OK, heres the structure of the new tape format file... it consists of
blocks, just like normal .TAP file, but it has some more information in them :)

btw. Can someone propose a name for this tape format ( and extension ... since
.??? is illegal ;))) )

note: There are some games ( like BubbleBobble ) that NEED the blocks to be
      without ANY pause between them... therefore the pause block is necessary
      Maybe there should be another block type ... USUAL saved block...
      which could be just the same as .TAP block ... ???

Offset  Length   Description
    00      01   Block TYPE :  00 : Normal Block of DATA
                               01 : LEADER Tone
                               02 : Pause
                               03 : Indefinite Pause (i.e. between Levels)

  00 - Normal Block :

    01      02   Length of Half Period (half of ___--- wave) in Z80 clock ticks
                 ( would 1 byte suffice for this ? I guess it will ;) )
                 AND is it ALWAYS   bit 1= twice the length of bit 0 ???
                 ( if not then define separate lengths for 0 and 1 )
    03      01   Starting amplitude ( either ___ (-128) or --- (127) )
    04      01   Number of BITS in the LAST Byte (1-8)
    05      01   Is last BIT full length ( both ___ and --- ) ? (0-yes, 1-no)
                 ( is this one necessary ? )
    06      02   Number of Bytes of Data that follow
    08      ??   DATA

  01 - LEADER Tone :

    01      02   Length of Half Period (see above)
    03      01   Starting amplitude (see above)
    04      02   Is last Half Period full length (see above)
    05      02   Number of Half Periods
                 ( is 2 bytes enough ? )

    note: are the Starting Amplitude and "Is last h.perido full" really
          necessary ???

  02 - Pause :

    01      ??   Lenght of Pause ( either miliseconds or something else ??? )

Files can be appended together just like .TAP files can be ( with normal
COPY /B file1.??? + file2.??? outfile.???

Instead of being over complicated, how about this idea.

Type				marker
header (tone)			255
Pulse header			254	
Pause				253
tone 1 (standard load [0])	0
tone 2 (standard [1])		1
Various hyperload tones		2-252

That way, the file might be a bit larger than a .Tap file, but it'd be a
hell of a lot smaller than a sound sample file (Voc?).

If hyperloads where less varied than that, you could use nibbles instead of
bytes, with 13,14 and 15 being the header tones and pauses....

Seems quite sensible to me.....
