Proposed New ZX Tape format

16 posts, 1997-02-17 – 1997-02-27

1997-02-17 address hidden 

  This is a proposed .ZXT (.ZXTape) format with support for all kinds of Turbo
and Custom Loaders. I wrote something similar once before, but got almost NONE
response. I guess now that there is some more discussion on the subject someone
might find this interesting - especially the emulator writers. But primarily I
wrote this to use with my HypraLoader. First I wanted to use ZXS but gave it up.

  The file is identified with the first 6 bytes being 'ZXTape'. If most of you
want then it can be ommited... which would mean that you could link various
files together just like you can .TAP files.
  Then the body follows which is devised from blocks. Each block is identified
with its ID byte followed by its body. There are currently 4 types of blocks.

So the file structure is :  'ZXTape' ID1 Body1 ID2 Body2 ...
                             0       6   7     ...
Or without the 'ZXTape' Identification if it would please more of you :)

  The Two-Byte (Word) values are always stored LSB (Least Significant Byte)
First.
  The timings are given in Z80 clock ticks (or T states) unless otherwise
stated.   1 T state=1sec/3500000   !
  The values in the tables mean : Offset (in bytes), Length (in bytes
(i.e. 1 - byte, 2 - word)) and then the description.
  You might interpret full-period as one pulse (----____ or ____----) and
half-period as only one half of the pulse (---- or ____).

These are the possible blocks :

ID : 00  -  Change of Loading Speed
-------     By default the values in Brackets should be used. They represent
            the values used by the Spectrum ROM loading routine. If this block
            is never present then all blocks are saved with normal speed.
            If my default values are incorrect then please inform me !

00 2  Length of PILOT half-period     [2100]
02 2  Length of SYNC  half-period     [700]
04 2  Length of 0-bit half-period     [800]
06 2  Length of 1-bit half-period     [1600]

ID : 01  -  Pause
-------     If Pause value is 0 then there should be an Indefinite Pause
            (i.e. waiting for Keypress)

00 2  Length of Pause in mili seconds (ms)

ID : 02  -  Text Description
-------     The description can be upto 255 characters long, but please keep
            it down to about 30 so the programs can show it in one line !!!
            This is ment to identify parts of the tapes. So you know where
            Level 1 starts, where to rewind when you lose all the lives, etc.
            Ofcourse you Can use it in the beginning to Identify the name of
            the game or program used in the file.

00 1  Length of the Text
01 x  Text in ASCII

ID : 03  -  DATA Block
-------     This is the block with actual Data. It is very similar to the .TAP
            block but with some additional Info.

00 2  Length of PILOT tone (in PILOT full-periods) [2000 for Header, 4000 Data]
02 1  Length of SYNC tone (in SYNC full-periods)              [1]
      Some loaders don't use this at all, so for those Length of SYNC=0.
03 1  Used bits in LAST Byte (other bits should be 0 !)  [8]
      i.e. if this is 6 then the bits (x) used in LAST byte are: xxxxxx00
04 1  Starting wave (the Amplutude of FIRST half-period)      00=Low  FF=High
      i.e. if the first pulse of PILOT starts with ---- or ____
05 1  Reserved
06 2  Length of DATA that follows
08 x  DATA, the bits are saved MSb (Most Significant Bit) first

  This should do it for now! I think this format is much better than .ZXS and
is also MUCH more understandable. If you have ANY additions/corrections or any
other ideas please post them to comp.sys.sinclair. I am not exactly sure if all
spectrum loaders used the same coding (i.e. both half-periods are the same
length) or not. I went through the 50 or so custom loading tapes and all of them
have the same coding, only the timings differ. Some of them have NO pause
between blocks (the PILOT tone of the next block is basically continuation of
the current data part) - like StarStrike II and most of the Crash (or was that
SU) cover tapes. Anyway, I hope we can make a better tape format !

Regards,
  Tomaz
