Thanks for the ROM select option.
I noticed that there is also a hardware option to remove overwrite
protection from the ROM.

In that case,
POKE 5820,251 will ensure that LPRINT .00001 works correctly by causing 
the loop PF-ZRO-LP to begin by loading the accumulator with zero each
time.
POKE 5358,4 and POKE 5360,5 swaps the mult and div instructions in 
NXT-DGT-1 so that 
10 PRINT INT (.5+.5) gives the result 1 and not zero.

The only other modification I made was to incorporate Sir Isaac Newton's
square roots.
That involves too many POKEs but the ROM can be downloaded from here.

http://www.wearmouth.demon.co.uk/sg81.rom

The square roots are faster and more accurate
10 PRINT SQR 100  = INT SQR 100 
evaluates as TRUE and not false as on the standard ZX81, Spectrum
Commodore 64 etc.

2003-09-27 22:43:57 Mike Wynne Re: [ANN] EightyOne, another ZX81 emulator
<…@…> wrote...
> The ZX81 emulators already have their own fileformats anyway.
> .p and .81 files.

Well .p and .81 are essentially the same format with a different extension.
The problem with this format though is that it only allows one virtual file
to be stored per host file.  So, if a tape had 4 files on it each of those
files would have it's own .p file on your hard drive.

Obviously keeping track of which file goes with which program is tricky, and
a complete nightmare if two programs happen to use the same name.

At the moment, there is no standard file for holding an entire ZX81 tape in

How long will a TV wait for a Hsync pulse that obviously isn't coming?
2003-10-04 08:03:57 Richard Wilson Re: [ANN] EightyOne, another ZX81 emulator
Woody wrote:
> 
> How long will a TV wait for a Hsync pulse that obviously isn't coming?

It won't. The TV (usually) contains what is known as a PLL (Phase Locked
Loop) which generates the internal HSYNC signal used by the tube. The
PLL synchronises itself to the HSYNC signal input from (int this case)
the ZX display circuitry.

If no HSYNC signal appears for a whole scan line, the PLL will continue
to generate the internal signal at a frequency similar to that which it
was generating the last time it had steady HSYNC inputs, but will
probably increase the wavelength slightly to compensate for the lack of
an input signal. It will continue to increase the wavelength until it
reaches its minimum operating frequency (usually about 15kHz). Most
modern TV circuits allow horizontal frequency ranges of about 15kHz to
16.5kHz. Look for documentation on the LA7800 (used in the Amstrad
CMT644). You should be able to find a PDF datasheet.

I've found it very difficult on the net finding accurate, detailed
information about the way a real TV operates, especially the horizontal
deflection circuitry.

Not sure you quite got the idea there, but here are some facts:

If you have a HSYNC every 64us, and change it to 128us (i.e. skip every
second scan line) the TV will provide a steady picture. It inserts its
own internal HSYNC at approximately 64us. It would be nice to measure
this with a CRO to see where the intermediate internal HSYNCS actually
happen.

If you have a HSYNC every 64us, and you move the HSYNC by 1us:

ie. HSYNC ... 64us ... HSYNC ... 65us ... HSYNC ... 64us ... HSYNC (and
64us from here on)

The TV will take approximately 8 scan lines to move the position of the
internal HSYNC by 1us.

If you have a HSYNC every 64us, and you increase the wavelength to 65us:

ie. HSYNC ... 64us ... HSYNC ... 65us ... HSYNC ... 65us ... HSYNC
(etc.)

The TV will take approximately two whole frames (1/25th of a second) to
adjust its internal wavelength to 65us.

I haven't managed to test what actually happens when there is no HSYNC
for a prolonged period. It could do one of two things:

1. Adjust its frequency to its default free-running frequency (ie.
15.734kHz for the LA7800).

2. Adjust its frequency to its minimum operating frequency (ie.
15.734kHz - .750kHz for the LA7800).

The LA7800 is used in the Amstrad CPC CTM644 monitor, which is a
modified Amstrad TV (ie. It has the receiver removed).

During the vertical retrace routine, the ZX81 ROM checks bit 6 of it's port.
Depending on this value it then writes either a 55 or a 31 to the system
variable MARGIN.  The only consequence of this is that the NMI routines then
counts either 55 or 31 scanlines above and below the central displayable 192
lines.  This makes a complete frame of either 302 or 254 scanlines, plus the
vertical retrace itself.  The vertical retrace and the timing of each
scanline are identical for both PAL and NTSC '81s.
