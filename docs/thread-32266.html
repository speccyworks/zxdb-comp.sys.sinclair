2006-05-29 13:43:30 John Elliott 
Newsgroups: comp.sys.sinclair,comp.sys.amstrad.8bit,rec.arts.int-fiction

  A new version of ZXZVM (a Z-code interpreter for the Sinclair Spectrum and
Amstrad PCW) has been released. New features include:

- The Spectrum version now supports ResiDOS.
- The Spectrum version can now operate in 32-column mode, as well as
 64-column.
- The Spectrum version allows the screen colours to be changed during play 
 (using cursor up / cursor down).
- The interpreter core can now start Beyond Zork without crashing.
- The text formatting in the MST3K games has been improved.

  My thanks to Garry Lancaster for the Spectrum-specific improvements.

ZXZVM can be downloaded from its homepage
  <http://www.seasip.info/ZX/zxzvm.html>
or from the IF-archive
  <http://www.ifarchive.org/indexes/if-archiveXinfocomXinterpretersXzxzvm.html>

It runs through a *massive* number of functions each turn - every rule is a 
function, and many of them have to be checked at least once every turn, and 
sometimes multiple times, to see if they apply (and procedural rules are

to 5 worn garments, there's a *noticeable* pause - about 5 seconds - and 
this is on a fairly fast PC!

The standard I6 world model doesn't have all these rule checks - you check 
the before function for the noun (a single function call), the after 
function, and possibly a couple of react_* functions.

> > that creates the CPU overhead?
> 
> It runs through a *massive* number of functions each turn - every rule is a 
> function, and many of them have to be checked at least once every turn, and 
> sometimes multiple times, to see if they apply (and procedural rules are 
> even worse!

I have not analyzed the generated code in detail, but my sense is that
most I7 features are only a constant-factor worse than an equivalent
I6 feature. Roughly the same number of things are happening. The
difference is that instead of a single attribute check, property
check, or function call, you get a rulebook or activity check. (Which
are still function calls -- they're just heftier functions.)

Now, as you say, procedural rules are worse. They have a relatively
heavier impact than most I6 customizations, because every procedural
rule is run on every rule check. (Their actions are expensive, too.)
So I am not happy that the most common kinds of library-message
modifications require procedural rules in I7, and I've been putting in
feature requests to be able do that sort of thing at compile time.
(Ideally, you shouldn't need a procedural rule unless you want the
system behavior to change *during* the game.)

Another particularly bad hit is I7 object specifications. Don't get me
wrong, I like them and I don't want to think about "objectloop"
statements ever again. But a lot of the things I did with I6
objectloops "in" or "near" something -- loops which iterated only over
the contents of a single container or room -- wind up in I7 code as
iterations over the entire game world. A scope search in I6 may wind
up (in I7) as an iteration over the game world with a scope search at
*each* step.

It is possible that more optimization will go into the compiler as it
evolves. But considering the number of bug reports I'm still sending
in, I don't demand optimization this week. :)

> The standard I6 world model doesn't have all these rule checks - you check 
> the before function for the noun (a single function call), the after 
> function, and possibly a couple of react_* functions.

That's misleading. The "couple of react_* functions" are handled by
doing a complete scope search at "before" time, and then another at
"after" time. The cost of the search usually outweighs the cost of the
customizations. 

I7 actually saves this effort in the simple case -- it doesn't do such
a search unless there's a rule with a "visible" condition. On the
other hand, if there are several such rules, I think it does several
scope searches. (Not sure of that, however.)

Hi John,

when I tried to run the first I7 examples, I also noticed the slowdown.
I had taken some measurements with different profiling tools, which I
unfortunately did not keep or document. The biggest differences I had
noticed from the profiler runs were as I remember:

- many more instruction executions between turns in "Bronze" and at the
start of "ROTA", older games usually only execute a couple of

access as well as the instruction decoding step which led to a
significant speedup.

For what it's worth, I suspect these may not be representative of what
would happen with all I7 games. ROTA does a lot of computational setup,
and Bronze relies heavily on pathfinding throughout -- even when the
player is not actually moving from room to room, it is doing a little
pathfinding to determine whether adjacent rooms are visited or not,
correctly name doors, and so on. So it is probably possible to write an
I7 game that does not run quite so sluggishly if one avoids some of the
newer and more intensive features. (But having a faster interpreter is
still unquestionably better.)

The +3DOS overhead is certainly pretty significant, so adding your own
caches can only be a good thing. However, don't expect to be able to
run ROTA at a playable speed with just that change... I tried running
ROTA under ZXZVM v1.11 on ResiDOS with a 512K ZXCF interface - this has
enough memory to load the entire story, so the +3DOS routines are never
called during play. It "only" took 1m30s to display the intro, and a
further 1h 18m 45s to get to the first prompt. Typical responses to
inputs were 3m30s (inventory) and 3m45s (north).

However, Inform6 games are (just about) playable. Vespers (approx the
same size as ROTA) takes 48s to get to the first prompt; typical
responses were 19s (inventory) and 39s (west).

Similarly, a smaller/older game, Edifice, took 20s to the first prompt,
8s for an inventory and 23s for "examine rock".

As a point of note, ROTA is also pretty slow on my Palm (running
CliFrotz). It takes 2m50s to get to the first prompt, and then about
9-10s for typical responses (inventory/north).

As well as the performance boost from caching data and code pages, it also fixes a bug in the @call_vn opcode with a zero argument (If you're interested, older versions treat it like @call_vs, which means the instruction stream gets out of sync).
The problem's easily reproducible with release 31 of The Hitchhiker's Guide to the Galaxy (release 871119):

GET UP
LIGHT
TAKE GOWN
WEAR GOWN
LOOK IN POCKET
EAT ANALGESIC
S

Versions 1.11 and earlier will abort with an 'Illegal instruction' error. Version 1.12 will (I hope) work normally.
