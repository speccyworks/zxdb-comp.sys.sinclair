The sprite pack C library for the z88dk C cross compiler is now
available from:

http://justme895.tripod.com/main.htm

Now you can write games for the spectrum in C!  The process is
simple: 

 1. Write C program.
 2. Run batch prog to create a tap file.

Five demos in tap format can be downloaded from the site, with
C source available.  Two you've seen already (a pattern fill
and ten windows floating around).  The third is a C version
of the test program bundled with the assembly API for speed
comparison.  The fourth is an experiment in registering a C
interrupt service routine.  The final one tests reading from
stdin and writing to stdout.

The z88dk C compiler seems to me to be a nearly complete
ANSI-C compiler.  You can get it from:

http://z88dk.sourceforge.net/


Enjoy,
Alvin

> By the way, I'm curious to know what the "Sprite Pack Display List"
> structure is and why it consumes 24K of RAM!

It doesn't actually occupy the full 24k, there are free holes
scattered around inside it.

The display list contains 4 bytes per character square: a pointer
to a background tile and a pointer to a linked list of sprite
char structs.  So it really occupes 4*768=3072 bytes
(see "Internal Details->Display list" and "Memory maps->spectrum"
for more details).

The display list actually occupies the following addresses (hex):
8000-801f
8100-811f
8200-821f
...
df00-df1f

And available memory can be found at (not the *** here):
8020-80ff
8120-81ff
8220-82ff
...
df20 and up

The reason that it's scattered all over the place is because
it's very quick to calculate the address corresponding to a
particular character coordinate.  This is one of the compromises
I made to improve performance.  I found that writing this kind
of code for the spectrum was very stressful -- I was always
sweating about whether what I was doing was going to be
fast enough :).

*** Not all of that memory is actually free.  I put a dirty
chars map in there (actual size = 96 bytes, marks which characters
need to be updated), which means the free memory actually runs from
0x??39 to 0x??ff.

I took some of that and added it to queue #0 (dynamic block memory
allocator) in 14-byte chunks.  These chunks are used to allocate
sprite structures and char structs that make up the sprites.
(Around 250 blocks in total, mentioned in the programmer's intro).

So I left the following for users to harvest:

9439..94ff
9539..95ff
9639..96ff
...
de39..deff

which amounts to a sizeable 14925 bytes free inside the display
list.  One of the reasons I included the block memory allocator
is to help to organize that memory and I used it a couple of times
in the demo programs.

So there you go, the full story!

> 9035 bytes of memory for
> the compiled C code may be a tad limiting in some circumstances.

Yeah, I know :)  I did my best at the time.  You can feel
better about a couple of things:

Calls to sprite pack take up almost no memory because the binary
is already in place and the C compiler doesn't have to append
the code to the C program.

When you use the z88dk libraries, you receive a one-time hit
to append the library code.  stdio is especially big: if you
touch the printf / scanf stuff, your program size will
jump about 2k to get the stdio library code.  But thereafter
multiple calls to stdio are practically free.

> Will
> this overhead be reduced when a version of Sprite Pack that fits in with
> z88dk's linker is available?

Yes.  The next version is going to do away with data structures
in fixed memory locations and convert them to tables (at a small --
I hope! -- performance cost).  This will do two things: there will
no longer be an artificial constraint on where the C code can go and
free memory will no longer be scattered all over the place since the
table, well being a table, will be compact and will be incorporated
into the C binary.

I'll also be adding full support for the ay chip and I'm thinking
hard about removing colour information from background tiles and
making colour a property of the character square.  Possibly a
pointer to a colour in a pallette table.  That would improve
compatibility with the Hi-Colour version...


Well, that was long and dry!  Anyway, I'm glad I've sparked your
interest.  I have to admit, the prospect of programming in C for
the spectrum gets me all wound up as well :)
