11 posts, 1997-07-06 – 1997-08-08

1997-07-06 …@… 
I've recently been converting a load of "Your Sinclair" covertapes
to the TZX format with Taper, and discovered that SAM Coupe programs 
seem to convert fine as well (on the default settings). 

Would somebody with a SAM & Taper like to test these out, to see if
they have indeed converted correctly?
Alternatively, is there a Coupe emulator around which supports
tape loading?

I'd also be very interested to know the specifics of the Coupe's
tape format (timings, header layout etc), as this could perhaps
be incorporated into the TZX format.

I've converted 4 SAM programs so far, and the average timings seem
to be:
   PILOT pulse: 1340T
   PILOT length: 6000 pulses
   Sync 1: 612T
   Sync 2: 350T
   ZERO bit: 550T
   ONE bit: 1100T

Although the blocks all convert correctly with the right parity byte,
all of them have extra bits afterwards: 7 bits in half the cases &
8 bits in the other half. Whether it's 7 or 8 bits, the "last byte"
is always 02. Does anyone know why this is?

Header blocks seem to be of length 80 with a flag byte of 1, and
data blocks have a flag byte of 255.

The default Sam tape format is identical to that of the Spectrum,
except that, as you note:

>Header blocks seem to be of length 80 with a flag byte of 1, and
>data blocks have a flag byte of 255.

Exactly what data goes into the header is mentioned in the technical
manual, but I don't have the details with me.

The loader contains a trick so that if you set the flag to 1 and it
actually finds a zero then it will continue as if it matched and also
set the length to 17.  This allows you to load a Spectrum header when
you were expecting a Sam header (if you type LOAD "" CODE you can play
in a Spectrum code file).

I believe the higher and lower tape speeds on the Sam are similar to the
normal speed with the numbers scaled up or down in proportion, but I
couldn't guarantee it.

In article <…@…>, …@… wrote:
>Can I ask you if you can provide the exact timings ? (Any time is good time...
>no hurry what so ever). Since I would love to include them in the TZX file
>format.

>What about that extra byte (or 7 bits) after the XOR Checksum in SAM blocks ?
>Why are they there ?

OK, my calculations are as follows.  No particular guarantee that they
are correct.  :-) The Sam tape saving routine appears to be written a bit
more sloppily than the Speccy one so the times are a bit irregular.  In
addition, I think the ULA will add some wait states when the Sam tries
to access the tape port and the paging port, but I don't know how many.
Consider rounding the times up to the nearest multiple of 8.

Notes:
  - The sam's clock speed is 6MHz.
  - There is a system variable (which you can set by executing the command
    DEVICE Txxx where xxx is the desired number) which sets the speed.  The
    usual number, I believe, is 112.  I refer to this as n below.
  - Some of the timings below differ by one cycle depending on whether
    the next bit to be saved is 1 or 0. The notation +nxtbit means add
    one cycle if the next bit is a 1.
  - All times are half-cycles, that is, the time from one OUT to the next.
    A full cycle has two OUTs, of course.

The normal leader tone has a half-period of 99+32n cycles.
Then there is one half-cycle of period 145+32n.
The first sync pulse has a period of 99+16*ceil(n/2) and the second
has a period of 194+16*ceil(n/2)+nxtbit.

Within a byte, the first pulse of a zero-bit is 33+13n cycles, and
the second pulse is 32+13n+nxtbit.  A one-bit has timings 72+26n and
71+26n+nxtbit.

The second pulse of the last bit in a byte usually takes 15 cycles less than
usual (although there are two extra IN instructions here so the ULA might
add some more cycles).  However, if an exact multiple of 64K bytes remain
then it takes 16 cycles more than usual, unless this is the last byte or
the parity byte, in which case it is only 6 cycles more.  In addition, if
the next byte lies across a page boundary then it takes 13 extra cycles to
fetch it.

Now, because the fetching of the next byte occurs during the second pulse
of the last bit of the previous byte, this means that after the last byte
has been saved there is still one OUT instruction to go, to finish the
current pulse.  It seems that rather than coding this directly, the ROM
author decided to save another junk byte.  Hence there are an extra 7.5
bits of junk after the XOR checksum byte.  I think these always represent
the number 2, as it happens.
